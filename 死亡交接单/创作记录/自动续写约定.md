# 自动续写至完结

## 授权与目标

作者最新指令：“自动继续后续所有内容直至完结”。此指令替代早期“每批结束等待继续”“只试写三章”的工作节奏，保留已经确认的故事、文风与分部分提交要求。不得重复询问是否继续。

唯一作品仓库：qingyuun/story-docs，分支 docs，作品根目录“死亡交接单”。持续完成约60万正文汉字、六卷、约180—200章的《死亡交接单》；章节数量按叙事容量调整，不能将长篇突然压缩成短结局，也不能循环填充达标。

## 每次接续

1. 先从远程 docs 读取当前提交和“创作记录/写作计划.json”，再读本文件、总纲、人物档案、规则与伏笔、创作约定、最新连续性摘要、相应细纲及最近两章全文。以仓库最新内容为准，不能从自动任务启动时的旧章号覆盖后来进度。
2. 恢复未完成章节或续写 next_chapter。每次至少完成一章，通常完成1—3章；这只是单次执行容量，不是等待作者批准的关卡。缺少细纲则先按既定卷内因果补细纲，然后写正文。每卷完成后先检查并修补该卷，再进入下一卷。
3. 章首兑现上一章问题、约定或行动；跨日、换地点、切换视角交代清楚。严禁用互不相干的事件拼接章节。未解决的问题要有实质阻力、行动及结果，不能让人物反复询问同一事项延长篇幅。
4. 完整场景正文通常3000—3800汉字，长短服务情节；不以大纲、摘要、标题、标点计算字数，不大量生成占位章节。每章只用一个有限视角，双主角比例服从故事。无爱情线。
5. 写后人工审读并检查章间因果、角色知识、时间、金额、物件保管、证据来源和伏笔；脚本实际可用才运行，不冒称运行缺失工具。脚本不可用可用实际程序计数并记录人工检查，不能因为缺某一套技能运行时而停止写作。
6. 同步章节摘要（含章末状态）、写作计划、校审记录、README目录与总字数；必要时更新人物和伏笔。规划不等于已发生，推测不等于确证。每章及其状态记录作为一部分提交至 docs；完成一部分即提交，不能积攒到全书结束才保存。
7. 优先使用可用工作区和既有Git流程；没有工作区时使用已连接的GitHub工具读写。多文件提交可通过 create_tree（在现有tree上增加变动）、create_commit、update_ref 完成，update_ref 使用 expected_sha 且 force=false；不得用不含其余文件的新空树替换整库。遇到分支前进先读取差异、重新衔接，不强推覆盖。仅能逐文件更新时先提交正文，再同步状态；失败后的下一次运行需恢复这一部分，不重复写同一章。
8. 不并行启动多个写作任务或子代理。提交前检查远程是否已有人推进；若有，先重读接续。用户新的修订、暂停或停止指令优先。

## 六卷兑现与长度预算

沿用“大纲/总纲提案.md”：现场干预费约9万；免死订金约10万；遗物持有人约10万；三年前的现场约11万；死亡证明约10万；交接之后约10万。细纲滚动设计，不为凑满章数复制同类案件。

首卷交代资料投放、郝建新被诱导到场、干预费验收及现实证据；卷末才识别许照报价短信。第二卷展示一次无人替死的成功避险及原件变化、照片固定。第三卷揭示许照参与并退出，双方隐瞒有具体后果并修复。第四卷重建旧事故，不洗去陈砚真实失误或许照过错。第五卷查清死亡订单的资金与执行。第六卷靠共享信息和正常救援破坏交易，主要责任人被捕，以合理时间跨度交代案件和生活后续。

注意总纲中需要在写前明确的边界：首卷末陈砚姓名的残本日期不完整，不能把它直接认作数月后的准确预言。残本仍只反映近期条件；后续死亡订单是人为行动材料，必须交代当时的新风险及版本，不得借一张早期残本违反近期规则。

## 完结与停止条件

只有六卷实际正文完整、核心案件与旧案因果交代、主要角色结果落地、伏笔回收经过检查、目录和统计一致、末章及相关记录已提交远程，才可将写作计划的 book_status 改为 completed。没有这些条件，批次完成必须保持 book_status=in_progress。

完成后生成“创作记录/完结校审.md”，列正文实际总量、六卷收束、主动保留的异常疑问及仍未做的外部查重等事项。最终一件封存异常物的新变化只留下边界疑问，不用新主谋或新死者推翻已完成案件。

当上述完结记录已在远程，停用执行本约定的自动任务，并报告全书目录及最后提交。此前每次执行报告本次实际完成章节、累计正文量、远程提交及下一步，不能宣称全书已完成。

## 运行状态

此文件是可恢复工作约定，不是后台任务已启用的证据。调度是否成功以自动任务工具的返回结果为准；任务标识确认后另写“创作记录/自动任务状态.json”。访问或提交失败时明确报告阻碍，不写虚假的完成状态。
